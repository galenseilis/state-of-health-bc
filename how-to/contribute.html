How to contribute

Set up

  1. Clone the repository:

    git clone https://github.com/galenseilis/state-of-health-bc.git
cd state-of-health-bc

  2. Install Quarto (version 1.4 or later) and uv.

  3. Create the Python environment (installs the sohbc package and the development tools):

    uv sync

  4. Preview the documentation site locally:

    quarto preview

Edit documentation

  • Documentation source lives in the four Diátaxis directories: tutorials/, how-to/, reference/, and explanation/.
  • The site configuration is _quarto.yml; the landing page is index.qmd.
  • Decide which Diátaxis section your page belongs in before writing: learning → tutorials, task → how-to, fact lookup → reference, understanding → explanation. See the project structure reference.

Check your page renders cleanly:

quarto render

Cite as you go

Factual claims about the world — statistics, definitions, attributions, descriptions of sources — should be cited:

  1. Add the source to references.bib (BibTeX). Verify the URL loads before adding it; never guess a URL. Prefer primary sources (the issuing organisation’s own page) over secondary reporting.
  2. Cite it inline with Pandoc citation syntax: [@key] for a parenthetical citation (renders as “(Author Year)”), @key for a narrative one.
  3. Render — each page generates its own reference list containing only the works it cites.

Project decisions and plans (milestones, scope choices, conventions) are documented in the roadmap rather than cited. When in doubt, cite.

Contributing code

The language policy balances a clear top-level framework with speed where it actually matters:

  • Python is the main language for gluing together the top-level framework and interface — orchestrating stages, wiring pipelines, and presenting results.
  • Python may also act as glue around other tools — including other programming languages, such as R — whenever there is a distinct benefit: a mature statistical or domain library, official bindings, or ecosystem tooling not worth reimplementing.
  • Where performance matters and new functionality must be written, the primary implementation is in Rust, C, and/or C++:
    • Prefer Rust for completely new (greenfield) performance code.
    • C and C++ are allowed for interfacing with existing low-level libraries that already exist, when that is useful.

If it is unclear which case applies to your change, open an issue and ask before writing the code. Run the tooling tests before submitting:

uv run python -m unittest discover -s tests -v

Submit changes

  1. Create a branch for your change:

    git checkout -b my-change

  2. Commit your work with a clear message describing the change.

  3. Open a pull request against main.

  4. The CI workflow runs the test suite, and the documentation workflow builds the site, on every push to main; failures in either indicate a problem to fix before merging.

Where work is planned

Milestones and their deliverables are tracked in the roadmap. If you want to pick up work, start with an in progress or not started milestone and open an issue to say you are taking it.
